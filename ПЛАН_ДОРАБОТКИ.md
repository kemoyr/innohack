_Составлен на основе полного разбора архива `final_beeline_project.zip` и анализа целевой ВМ (домен `auroraclient.fun`)._
_Дата: 2026-07-16._

## 0. TL;DR — вердикт

Проект **функционально почти готов** и уже закрывает ~80% ТЗ: есть учёт волонтёров, статистика, календарь с явкой, рейтинг с пьедесталом и достижениями, плюс бонусом — Telegram-бот, верификация мероприятий по фото/гео/QR и ИИ-модерация. Стек современный (FastAPI + React + Tailwind + Recharts), код аккуратный.

Но **в текущем виде показывать руководству нельзя** без правок. Есть 3 блокера:

1. **🔴 Утечка данных**: публичный эндпоинт `GET /api/volunteers/{id}` отдаёт **хэш пароля, email, телефон, telegram_id** любому анониму. `GET /api/volunteers` (список) вообще без авторизации.
2. **🔴 Демо-данные «протухли»**: все мероприятия датированы мартом–апрелем 2026. Сегодня июль 2026 → график активности за 14 дней **пустой**, плитки «за неделю/за месяц» показывают **нули**. Дашборд выглядит сломанным ровно на тех виджетах, которые демонстрируют «жизнь» проекта.
3. **🔴 Секреты в репозитории**: в `.env.example` лежит **реальный `BOT_TOKEN`** и `SECRET_KEY=abc`. Токен нужно немедленно отозвать (он утёк в архиве).

Плюс серия мелких «косметических» проблем (захардкоженный `localhost`, off-brand фиолетовый favicon, нет мобильного меню) и редизайн под фирменный стиль билайн.

Ниже — что именно и в каком порядке доделать.

## 3. 🔴 P0 — Критические проблемы (обязательно до показа руководству)

### 3.1. Утечка персональных данных и хэшей паролей
- **Где:** `bot/api/routes/volunteers.py` → `get_volunteer_detail` возвращает `{**vol, ...}`, где `vol` = `SELECT *` из `get_volunteer_by_id`. В ответ попадают `password_hash`, `email`, `phone`, `telegram_id`.
- **Как эксплуатируется:** фронт зовёт этот эндпоинт как **публичный** (`api.getVolunteer` → `publicRequest`), т.е. **любой аноним** по `GET /api/volunteers/{id}` получает хэши паролей всей команды.
- **Также:** `GET /api/volunteers` (`list_volunteers`) — **без `Depends(get_current_coordinator)`**, отдаёт телефоны всем. В `api.js` он помечен как авторизованный, но сам роут защиты не имеет.
- **Фикс:** ввести «публичную» проекцию волонтёра (только `id, full_name, city, points, status, submissions_count, achievements, reviews, organizer_rating` — без `password_hash/email/phone/telegram_id`). Приватные поля отдавать только координатору. Навесить `Depends(get_current_coordinator)` на список `/api/volunteers`.

### 3.2. «Протухшие» демо-данные (дашборд выглядит мёртвым)
- **Где:** `demo_data.py` и `bot/database.py::_seed_demo_data` — даты мероприятий жёстко `2026-03-10 … 2026-04-15`.
- **Симптом на дату июль-2026:** `GET /api/stats/charts` строит окно «последние 14 дней» → ни одно мероприятие не попадает → **график активности пустой**. `get_stats` считает `this_week/this_month` по `scheduled_date >= начало недели/месяца` → **0 и 0**.
- **Фикс:** генерировать демо-даты **относительно текущей даты** (`today - N дней` для завершённых, `today + N` для запланированных), а не хардкодом. Заодно раскидать `created_at` у submissions/achievements по последним дням, чтобы «Лента активности» и «время назад» выглядели живыми.

### 3.3. Секреты в репозитории
- **Где:** `.env.example` содержит настоящий `BOT_TOKEN=8619591125:AAE...`, `SECRET_KEY=abc`, `ADMIN_PASSWORD=123456`.
- **Фикс:**
  1. **Отозвать/перевыпустить бот-токен** через @BotFather (текущий считать скомпрометированным).
  2. В `.env.example` оставить только плейсхолдеры (`BOT_TOKEN=<your_token>`).
  3. На проде задать длинный случайный `SECRET_KEY` и сильный `ADMIN_PASSWORD` через переменные окружения (не в файле в git).
  4. Убедиться, что `.env` в `.gitignore` (уже так) и не попал в архив/репо.

### 3.4. Захардкоженный `localhost` в проде
- `frontend/src/pages/SettingsPage.jsx`: ссылка «API документация» → `http://localhost:8000/docs` (битая на проде); ссылка на бота `t.me/Beeline_dashboard_bot` захардкожена.
- `bot/strings.py::DASHBOARD_LINK` = `http://localhost:8000` — кнопка «Открыть дашборд» в боте ведёт в никуда, если не задан `WEBAPP_URL`.
- **Фикс:** относительный `/docs`, ссылку на дашборд/бота брать из конфигурации (env/`WEBAPP_URL`), а не из констант.

### 3.5. CORS
- `bot/api/app.py`: `allow_origins=["*"]` + `allow_credentials=True` — некорректная комбинация по спецификации CORS (браузер отвергает credentials при `*`). Сейчас не критично (используем Bearer-токены, не куки), но при отдаче фронта и API с одного домена CORS вообще можно сузить до своего домена или убрать `allow_credentials`.

## 4. 🟠 P1 — Функциональные баги и «выглядит сломанным»

1. **Нет мобильного меню.** `Sidebar` — `position: fixed; w-64`. На `<768px` `App.css` убирает отступ контента (`margin-left:0`), но сам сайдбар остаётся поверх контента и перекрывает его. Нужен бургер + выезжающий drawer + оверлей. (ТЗ-аудитория — подростки/родители, заходят с телефонов.)
2. **Явку с веба проставить нельзя.** Завершение мероприятия с вводом `attendance_count` есть только в боте (`coordinator.py`). На вебе координатор может лишь создать мероприятие; кнопки «Завершить / указать явку» на `Calendar.jsx` нет, хотя `PATCH /api/events/{id}` это умеет. Добавить действие в карточку/страницу мероприятия для координатора.
3. **Номинации не автоматические.** ТЗ прямо просит «самый младший слушатель», «самая большая аудитория». Сейчас это статичные бейджи в демо. Реализовать вычисление: «самая большая аудитория» = событие с max `attendance_count` (и его волонтёр); «рекорд явки/города» и т.п. «Возраст слушателя» в модели не хранится — либо добавить поле, либо заменить номинацию на реально доступную метрику.
4. **Публичный дашборд показывает то же, что и приватный.** `SmartRoute` в `App.jsx` для неавторизованных отдаёт `Dashboard` с полной статистикой и списком топ-волонтёров. Решить продуктово: это ок (витрина) или обзорные цифры для анонимов надо урезать.
5. **Статусы событий рассинхронизированы.** В БД у `events.status` допустимы `pending/planned/completed/cancelled/rejected`, но `get_public_events` отдаёт `planned/completed/cancelled`, а пирог на дашборде считает только `planned/completed/cancelled`. `rejected`/`pending` нигде в публичных срезах не учтены — проверить, что это осознанно.
6. **Тип мероприятия не структурирован.** «Лекция/мастер-класс/воркшоп» сейчас только в тексте `title`. Для статистики «сколько лекций/МК провёл волонтёр» (ТЗ п.2) нужно поле `event_type` (enum) + фильтры/разбивка.
7. **Двойная проверка QR слабая.** `mark_qr_used` проверяет только пару (qr, volunteer) в submissions — один и тот же QR может использовать другой волонтёр повторно без ограничения по событию/времени. Для демо ок, для «реализации» — усилить.

## 5. 🎨 Редизайн под фирменный стиль билайн

Хорошая новость: макет **уже жёлто-чёрный**, поэтому это «донастройка токенов + ребрендинг», а не переделка. Двигаемся, «сильно не уходя от текущего стиля».

### 5.1. Палитра (Tailwind-токены)
Файл `frontend/tailwind.config.js`. Текущий `primary-500 = #FFC800` заменить на фирменный жёлтый билайн и выровнять шкалу:

```
primary (билайн жёлтый):
  500: #FFCC00   (ядро бренда; сейчас #FFC800 — почти оно)
  400: #FFD633
  600: #E6B800
  700: #B38F00
  100: #FFF6CC   (светлый фон бейджей)
чёрный: #000000 (фирменный, уже используется как bee-black)
белый:  #FFFFFF
```
- **Акцент оранжевый** (`accent-*`) свести к минимуму: билайн — это почти монохром жёлтый+чёрный+белый. Оставить оранжевый/emerald/red/amber только для семантики статусов (успех/ошибка/ожидание), но не как декоративный акцент. Бронзу на пьедестале/бейджах перевести в нейтрально-жёлтую гамму.

### 5.2. Брендинг
- **Название.** Заменить «Volunteer+» на со-брендинг билайн. Предлагаю по умолчанию: логотип-вордмарк **`билайн`** (строчными, как в фирстиле) + подпись раздела **«Дашборд координатора»** / «Штаб кибердружины». Затрагивает: `Sidebar.jsx`, `PublicNavbar.jsx`, `Login.jsx`, `Register.jsx`, `index.html` (`<title>`).
- **Favicon.** Сейчас в `index.html` фиолетовый (`#4f46e5`) «V+» — **off-brand**. Заменить на чёрно-жёлтый знак (жёлтый круг / буква на чёрном).
- **Логотип-бейдж.** Квадрат `V+` заменить на фирменный мотив: жёлтый круг на чёрном (отсылка к знаку билайн) или чёрно-жёлтая «полосатая» плашка. Не тянуть точный логотип-пчелу из-за прав — сделать узнаваемый стилизованный знак.

### 5.3. Мелочи стиля
- Верхняя полоса на экранах логина (`Login/Register`) уже жёлтая — оставить, подвести под точный `#FFCC00`.
- Тултипы графиков (`#1A1A1A` фон, `#FFC800` акцент) — подвести жёлтый под `#FFCC00`.
- Пьедестал (`Ratings.jsx`, `Leaderboard.jsx`): 1-е место — жёлтый градиент (ок), 2/3 — нейтральные; убрать оранжевую бронзу в пользу тёмно-жёлтой/серой.
- Шрифт оставить Inter (близок к геометрическим гротескам фирстиля). При желании — самостоятельный хостинг шрифта вместо Google Fonts.

### 5.4. Объём работ по редизайну
Правки в ~8 файлах, **логику не трогаем**: `tailwind.config.js`, `index.html`, `index.css`, `Sidebar.jsx`, `PublicNavbar.jsx`, `Login.jsx`, `Register.jsx`, плюс точечно тултипы/бейджи в `Dashboard/Ratings/Leaderboard`. ~0.5–1 день.

## 6. 🚀 Деплой на `auroraclient.fun`

### 6.1. Что уже на ВМ (важно!)
- **nginx** (активен, порты 80/443) обслуживает:
  - `auroraclient.fun` / `www` → **статический сайт-магазин** из `/var/www/aurora` (vhost `sites-enabled/aurora-site`).
  - `api.auroraclient.fun` → проксирует на `127.0.0.1:8080` — это **`aurora-core.service`** (отдельное API магазина, за Cloudflare, с rate-limit). Его **трогать не нужно**.
- Работают также **PostgreSQL** (5432) и **Redis** (6379) — для aurora-core. Нашему проекту они не нужны (у нас SQLite).
- **Порт 8000 свободен** — как раз наш бэкенд.
- **TLS** для `auroraclient.fun` уже выпущен (Let's Encrypt) — переиспользуем.
- Ограничения окружения: **`sudo` требует пароль**, `docker` не установлен, системный `python3` **без pip** (нужен venv через `ensurepip`), но есть **Node 20 + npm 10** (фронт соберётся), **git 2.43**.

### 6.2. Рекомендуемая схема (без Docker, нативно + systemd)
«Временно остановить другой сайт» = переключить **только apex-vhost** `auroraclient.fun` на наш проект; `api.auroraclient.fun`/aurora-core оставить как есть.

**Шаги (требуют `sudo`, т.е. участие человека с паролем):**
1. **Бэкенд как сервис.** Создать venv, поставить зависимости:
   ```
   python3 -m venv .venv && . .venv/bin/activate
   python -m ensurepip --upgrade && pip install -r requirements.txt
   ```
   Написать `systemd`-юнит `beeline-dashboard.service` (запуск `python bot/main.py`, `WorkingDirectory` проекта, env-файл с `BOT_TOKEN/SECRET_KEY/ADMIN_PASSWORD/DB_PATH=/var/lib/beeline/volunteer.db/DEMO_MODE`). Слушает `127.0.0.1:8000`.
   > Примечание: `bot/main.py` поднимает и бота (polling), и API. Если Telegram-бот на демо не нужен — можно сделать флаг и запускать только API (uvicorn) без polling.
2. **Фронт.** `cd frontend && npm ci && npm run build` → положить `dist` (напр. в `/var/www/beeline`).
3. **nginx.** Сохранить бэкап текущего `sites-available/aurora-site`. Переключить apex `auroraclient.fun` на новый корень + прокси API:
   - `root /var/www/beeline; try_files $uri /index.html;` (SPA-fallback)
   - `location /api/ { proxy_pass http://127.0.0.1:8000; ... }`
   - при необходимости `location /docs` и `/openapi.json` тоже проксировать.
   - Переиспользовать существующий сертификат `auroraclient.fun`.
   - `nginx -t && systemctl reload nginx`.
4. **Откат «магазина».** «Временная остановка» = просто вернуть старый vhost из бэкапа и `reload`. Данные магазина (в /var/www/aurora, postgres) не удаляем.
5. **Персистентность БД.** SQLite-файл вне репозитория (`/var/lib/beeline/…`), иначе демо-данные пересоздаются/теряются.
6. **API base на фронте.** Сейчас `API_BASE=''` (относительные пути) — при отдаче фронта и API с одного домена через nginx это уже корректно, менять не нужно.

**Альтернатива (Docker)** описана в `Dockerfile`/`DEPLOY.md`, но на ВМ Docker не установлен → нативная схема выше проще.

### 6.3. Вопрос портов/CORS
Т.к. фронт и API будут на одном домене (`auroraclient.fun` + `auroraclient.fun/api`), CORS можно сузить/убрать `allow_credentials`. `WEBAPP_URL=https://auroraclient.fun` — прописать в env, чтобы кнопки бота и ссылки вели на прод.

## 7. 🧹 Технический долг (P2, не блокеры)

- **N+1 и соединение-на-запрос.** Почти каждая функция в `database.py` открывает новый `aiosqlite.connect`; роуты `list_volunteers`/`leaderboard`/`list_events` в цикле делают доп. запросы на каждую строку. Для десятков волонтёров ок, но при росте — тормоза. Вынести общий пул/одно соединение, включить `PRAGMA journal_mode=WAL`, собрать агрегаты в один SQL с JOIN.
- **Дублирование схемы БД** в 3 местах (`database.py`, `demo_data.py`, `README.md`) — риск рассинхрона. Свести к одному источнику.
- **`README.md` в кодировке UTF-16** (ломается в обычных вьюверах, «рваные» пробелы) — перекодировать в UTF-8, почистить дубль-контент.
- **Нет тестов** и CI. Хотя бы smoke-тесты API (`/api/stats`, `/api/leaderboard`, auth) и линт фронта.
- **Нет error boundary / 404-страницы** на фронте; всё падает в белый экран при ошибке рендера. Спиннеры есть, скелетонов нет.
- **`datetime.utcnow()`** — deprecated в 3.12; заменить на `datetime.now(timezone.utc)`.
- **Ротация/размер загрузок.** `client_max_body_size` на нашем vhost задать под фото верификации (у aurora стоит `1m`). Временные файлы фото чистятся — ок.
- **healthcheck.** `railway.json` дергает `/api/stats` — для systemd/nginx это неактуально; для мониторинга лучше отдельный `/healthz`.
